Founder authorized Neon Free as development database after Supabase quota exhaustion; intended future production target Supabase Pro, subject to separate approval and migration QA. Do not switch to Firestore. Keep FastAPI, SQLAlchemy/Alembic and portable PostgreSQL. The database provider does not confer application security.

Observed: Vercel-managed Free organization; independent project creation was restricted. Founder then provisioned a project and authorized use. Selected project display name neon-cinereous-island, AWS US East, PostgreSQL 18.7. Original default branch main and neondb had zero public base tables, zero auth users and zero sessions. Created non-default child branch nur-path-dev with 0.25 CU bounds; readback ready. Real SQL SELECT 1 and current_database/version succeeded on child. The vector and pgcrypto extensions are available (not installed or tested here); zero public tables and auth users confirmed. Connector SQL session pg_stat_ssl.ssl=false; this describes that session only, not the external TLS termination or application's future connection. Require direct TLS verify-full (or equivalent certificate and hostname verification) for migrations and backend connection; verify with actual driver. No raw connection string/password obtained or published. No auth tables changed; no application schema applied.

Use the explicitly named development project/child branch only; re-resolve IDs privately and check project/branch identity before writing. Preserve parent branch and other projects. Use migrations as code, isolated CI PostgreSQL for destructive tests, dedicated non-owner application role with no BYPASSRLS, parameterized queries, object ownership checks and least privilege. Do not use database owner credentials for the running app. Pooled runtime connection and separate direct migration connection injected by secret manager. Do not expose a Data API or public buckets merely for convenience.

Existing Neon Auth schema is observed, not proof of usable authentication. Use provider-neutral identity and storage boundaries; evaluate managed auth with synthetic accounts when AUTH-001 is eligible. Neon Auth and Supabase Auth differ; validate account mappings, password reset/session invalidation and object migration before release. PostgreSQL major version compatibility must be checked against actual future Supabase target; use compatible SQL, extensions and tested export/restore, not Neon-only primitives. No paid services, live user data, main branch writes or production deployment.

CORE-002 remains IN_PROGRESS pending clean CI, Flutter analysis/tests, native scaffolding and scoped environment acceptance; DB-001 has not started. This is preflight evidence, not a production integration.
